1. موضع Architecture Patterns والغرض منها

ADM Techniques Chapter 4 — Reusable Knowledge for Recurring Architecture Problems
⌄

هذا الفصل الرسمي يقدم إرشادات لاستخدام Architecture Patterns. الفكرة أن Enterprise Architecture تواجه مشكلات متكررة عبر مجالات ومستويات تفصيل مختلفة؛ والPattern تحفظ خبرة سابقة في صورة قابلة لإعادة الاستخدام بدل إعادة اختراع الحل في كل Engagement.

Patternفكرة ثبتت فائدتها في سياق عملي، ويرجح أن تكون مفيدة في سياقات أخرى.

المغزى المعماري

Pattern ليست Copy/Paste لتصميم نهائي؛ بل معرفة منظمة تربط Context وProblem وForces بحل عام ونتائج وTrade-offs.

الهدف: إعادة استخدام التفكير والخبرة، وليس فقط إعادة استخدام مكوّن تقني.

2. لماذا Patterns مهمة في Enterprise Architecture؟

A Multi-Disciplinary Enterprise Needs Reusable Knowledge at Several Domains and Levels
⌄

Enterprise Architecture متعددة التخصصات: Business، Data، Application، Technology، People، Governance، Security، Operations. لذلك قد تظهر Patterns على مستوى Business Model أوInformation Flow أوIntegration أوPlatform أوOperating Model.

Reuse Proven Knowledgeالاستفادة من حلول تكررت ونجحت بدل بدء التحليل من الصفر.
Accelerate Designتقليل الوقت اللازم لاستكشاف Solution Structure والبدائل.
Make Trade-offs Explicitتوضيح ما الذي يتحسن وما الذي يتكلف أويتعقد.
Improve Communicationاسم Pattern يوفر Vocabulary مشتركة بين المعماريين وأصحاب المصلحة.
Support Consistencyتطبيق حلول متجانسة عبر عدة Initiatives ومناطق.
Connect Building Blocksبيان كيف تتعاون ABBs وSBBs داخل حل متماسك.
Enable Repository Valueتحويل Deliverables السابقة إلى أصول قابلة للاستخدام.
Reduce RiskKnown Uses وRationale يمنحان Evidence أفضل من التخمين غير المختبر.

3. خلفية الفكرة وتطورها

From Christopher Alexander and Buildings to Software and Enterprise Architecture
⌄
1979 — Christopher AlexanderThe Timeless Way of Building رسخ استخدام Patterns في Architecture المبنية.
Pattern LanguageA Pattern Language وThe Oregon Experiment وسعا فكرة شبكة Patterns المترابطة.
1994 — Software DesignDesign Patterns قدّمت حلولًا بسيطة وأنيقة لمشكلات متكررة في Object-Oriented Design.
Enterprise Architectureانتقلت الفكرة إلى نماذج وأساليب قابلة لإعادة الاستخدام تشمل software، hardware، networks، people.

التشابه بين معماري المباني ومعماري الأنظمة ليس في المواد، بل في التعامل مع Constraints وForces وبدائل متعارضة داخل Context محدد.

4. Building Blocks مقابل Patterns

Building Blocks Are What You Use; Patterns Explain How, When, Why, and with What Trade-offs
⌄
Building BlocksCapabilities أوComponents أوServices أوProducts. هي العناصر التي تبني منها Architecture: ABBs تصف الحاجة المعمارية، وSBBs تصف realization.
⇄
Patternsتضع Building Blocks في Context وتصف Problem، relationships، behavior، guidance، trade-offs، والنتائج المتوقعة.
امتحانيًا: Building Block عنصر؛ Pattern ترتيب ومعرفة قابلة لإعادة الاستخدام حول كيفية استخدام مجموعة عناصر.

5. Pattern ليست حلًا جاهزًا

A Pattern Is a Generalized Proven Solution, Not a Mandatory Product or Copy-Paste Blueprint
⌄

Pattern تصف حلًا عامًا لمشكلة متكررة داخل Context. قبل التطبيق يجب التحقق من Requirements وConstraints وForces وArchitecture Principles. قد تحتاج Specialization أوVariant، وقد لا تكون مناسبة أصلًا.

Reuse Blindlyنسخ Pattern دون التحقق من Context يخلق over-engineering أوmismatch.
⚖
Tailored Reuseاستخدام Rationale وForces وKnown Uses ثم تكييف Structure وBehavior.
الPattern لا تلغي Architecture Decision؛ بل تجعل القرار أسرع وأكثر قابلية للتفسير والمراجعة.

6. Content of a Pattern — الخريطة العامة

Common Pattern Elements despite the Absence of One Universal Format
⌄

لا يوجد Format واحد مقبول عالميًا لوصف Enterprise Architecture Patterns، لكن يوجد اتفاق واسع على العناصر التي يجب أن تحتويها معظم Patterns.

Nameاسم قصير ذو معنى.
Problemالمشكلة والهدف.
ContextPreconditions والحالة الأولية.
ForcesConstraints وQualities المتعارضة.
SolutionStructure + Behavior + Collaboration.
Resulting ContextPost-conditions وTrade-offs المتبقية.

ثم تضيف Pattern عادةً Examples، Rationale، Related Patterns، Known Uses، وقد تبدأ بـAbstract.

7. Name — اسم Pattern

A Meaningful and Memorable Handle for Reuse and Communication
⌄

وظيفة Name

جيد

قصير، مميز، يوحي بالIntent، يسهل إدخاله في Architecture Decision وRepository Search.

ضعيف

اسم Product محدد، أوعبارة عامة مثل “Best Architecture”، أواسم طويل لا يميز المشكلة.

الاسم يحول Pattern إلى مفردة داخل لغة الفريق. عندما يقول المعماري “Event-Driven Integration Pattern” يفترض أن بقية الفريق تستطيع الرجوع لتعريف مشترك.

8. Problem — المشكلة والIntent

Describe the Recurring Problem and the Goals the Pattern Seeks to Achieve
⌄

ماذا يجيب Problem؟

  • ما المشكلة المتكررة؟
  • ما Intent من تطبيق Pattern؟
  • ما Goals وObjectives؟
  • هل توجد Priorities أولية بين الأهداف؟

Problem يجب ألا تكون اسم الحل. قول “نحتاج Microservices” ليس Problem؛ المشكلة قد تكون independent deployment، scalability، وteam autonomy مع تعقيد domain مناسب.

9. Context — شروط قابلية التطبيق

The Preconditions and Initial State before the Pattern Is Applied
⌄

Context تحدد حدود الصلاحية

قد يشمل
  • نوع المؤسسة أوdomain.
  • مستوى النضج والمهارات.
  • Baseline systems وintegration style.
  • حجم الحمل والتوزيع الجغرافي.
  • Regulation وoperating constraints.
لماذا مهم؟

نفس Problem قد يحتاج Pattern مختلفة إذا تغير Context. الحل الجيد في مؤسسة Cloud-native قد يكون سيئًا في موقع disconnected أوregulated.

10. Forces — القوى والقيود المتعارضة

Expose the Qualities, Constraints, and Tensions that Make the Problem Difficult
⌄

Forces تصف ما يدفع الحل في اتجاهات مختلفة. الحاجة إلى Trade-offs هي غالبًا سبب وجود Pattern من الأصل.

Security & ReliabilitySecurity، robustness، fault tolerance.
ManageabilityMonitoring، operations، supportability.
PerformanceEfficiency، throughput، bandwidth، space.
ScalabilityIncremental growth on demand.
EvolvabilityExtensibility، maintainability، change cost.
Modularity & ReuseIndependence، openness، portability، composability.
CorrectnessCompleteness and correctness.
Usability & BuildabilityEase of construction and ease of use.

Forces تشبه Concerns وQuality Attributes التي يحاول المعماري تحسينها، لكنها تكشف أيضًا التفاعل والتعارض بينها.

11. Solution — البنية والسلوك والتعاون

Describe How to Achieve the Goals using Static Structure and Dynamic Behavior
⌄
Static StructureActors، components، services، building blocks، responsibilities، relationships.
+
Dynamic BehaviorInteractions، events، sequences، collaborations، state changes، failure handling.
+
Guidance & VariantsImplementation guidance، specialization، optional variants.

يمكن وصف Solution بالنص أوالرسومات. المهم ألا تكتفي بمربعات ثابتة إذا كانت كيفية التعاون والسلوك جوهر الحل.

12. Resulting Context — ما بعد التطبيق

Document Post-Conditions, Resolved Forces, Remaining Forces, and New Opportunities
⌄

بعد تطبيق Pattern

  • أي Forces تم حلها؟ وكيف؟
  • أي Forces ظلت غير محلولة؟
  • ما Trade-offs أوCosts الجديدة؟
  • ما Constraints الجديدة؟
  • ما Patterns أخرى أصبحت مناسبة؟

Pattern قد تكون خطوة واحدة نحو Goal أكبر. Resulting Context من Pattern قد يصبح Initial Context لPattern لاحقة.

13. Examples — أمثلة التطبيق

Illustrate the Problem, Context, Forces, Application, and Resulting Context
⌄

Example ليست مجرد صورة للحل؛ ينبغي أن تعرض سلسلة المنطق كاملة: Problem وContext وForces، ثم كيفية تطبيق Pattern، ثم Resulting Context.

Specific Problemمثال واقعي واضح.
Contextحجم، نضج، قيود، domain.
ForcesPerformance، security، cost، change.
Applicationكيف خُصصت Structure وBehavior.
Resultالقيمة والTrade-offs المتبقية.

14. Rationale — لماذا يعمل الحل؟

Explain the Internal Logic and Why the Pattern Resolves the Forces
⌄

Solution مقابل Rationale

Solution

تصف الشكل الخارجي والسلوك: ما المكونات وكيف تتعاون.

Rationale

تشرح لماذا ينجح هذا الترتيب، وكيف يحل Forces، ولماذا يعد اختيارًا جيدًا.

Rationale مهمة في Governance؛ بدونها يتحول Pattern إلى وصف يجب اتباعه بلا فهم، ويصعب تقييم صلاحيتها عندما يتغير Context.

15. Related Patterns — شبكة العلاقات

Predecessor, Successor, Alternative, and Co-dependent Patterns
⌄

Predecessor

Resulting Context منها يطابق Initial Context لهذه Pattern.

Successor

تطبق بعد هذه Pattern عندما يصبح Resulting Context مناسبًا لها.

Alternative

تعالج Problem نفسها لكن تحت Forces أوContext مختلفين.

Co-dependent

يجب أويفضل تطبيقها مع Pattern الحالية لكي يعمل الحل بصورة متكاملة.

هذه العلاقات هي الأساس لتكوين Pattern Language بدل قائمة Patterns منعزلة.

16. Known Uses وAbstract

Evidence of Proven Use and a Fast Orientation for the Reader
⌄
Known Uses

تطبيقات معروفة داخل أنظمة قائمة تثبت أن Pattern تصف حلًا مجربًا لمشكلة متكررة. وقد تعمل Known Uses أيضًا كExamples.

Abstract

ملخص افتتاحي اختياري يوضح المشكلات المستهدفة، الجمهور، والافتراضات عن القارئ.

Known Use لا تعني أن Pattern مناسبة لكل Context؛ هي Evidence على أنها ليست فكرة نظرية فقط.

19. Enterprise Architecture Patterns ليست Software Patterns فقط

Enterprise System Architecting Includes Software, Hardware, Networks, and People
⌄

الفصل ينبه إلى أن الأدبيات التقنية تستخدم Architecture أحيانًا بمعنى Software Architecture فقط. في TOGAF، المقصود أوسع: نماذج وأساليب قابلة لإعادة الاستخدام في architecting نظم معلومات المؤسسة.

SoftwareApplications، services، components.
HardwarePlatforms، devices، infrastructure.
NetworksConnectivity، topology، integration channels.
PeopleActors، roles، governance، operating responsibilities.

وقد تشمل Pattern أيضًا Business Processes وData وPolicies؛ لذلك يجب التصريح بمستوى ونطاق Pattern بدقة.

20. Patterns وArchitecture Continuum

Classify and Reuse Patterns from Generic Foundation Knowledge to Organization-Specific Assets
⌄

Architecture Patterns تعد نوعًا من Reusable Architecture Assets. المؤسسة التي تتبنى استخدامًا رسميًا للPatterns تدمجها عادةً في Enterprise Architecture Continuum وRepository.

Foundation / Genericمبادئ وتركيبات عامة جدًا.
Common SystemsPatterns لخدمات مشتركة مثل integration أوidentity.
IndustryPatterns خاصة بقطاع صحي أومالي أواتصالات.
Organization-SpecificPattern مخصصة ومثبتة داخل المؤسسة.

كلما اتجهنا نحو Organization-Specific زادت الملاءمة المحلية، بينما تقل العمومية وقابلية النقل خارج Context.

21. Patterns وArchitecture Repository

Store, Govern, Search, Validate, and Improve Reusable Pattern Assets
⌄

الفصل يذكر دمج Patterns في Continuum؛ عمليًا تحتاج المؤسسة Catalog أوLibrary داخل Repository حتى تتحقق قيمة reuse.

Captureاستخراج Pattern من مشروع أوsource خارجي.
Describeملء Name، Context، Forces، Solution...
ReviewArchitecture Board وdomain experts.
ClassifyDomain، level، continuum، applicability.
Reuseتطبيقها وتسجيل specialization.
Improveإضافة Known Uses وlessons learned.
هذه دورة تشغيلية عملية؛ لا يفرض الفصل الرسمي Tool أوWorkflow واحدًا.

22. Patterns وArchitecture Views

Patterns Help Design Models and Compose Views that Address Stakeholder Concerns
⌄
Stakeholder ConcernsSecurity، performance، operations، cost، interoperability.
→
Pattern-Guided ModelsStructure وbehavior وrelationships مجربة توجه modeling.
→
Architecture Viewsانتقاء أجزاء من النماذج لتجيب عن Concerns محددة.

Pattern لا تستبدل Viewpoint. Pattern تساعد في تصميم model؛ Viewpoint يحدد conventions؛ View تمثل Architecture الفعلية من منظور أصحاب المصلحة.

23. Patterns وBusiness Scenarios

Business Scenarios Can Reveal Recurring Problems and Candidate Patterns
⌄
Business Problemوصف challenge والنتائج المطلوبة.

24. متى تستخدم Patterns في ADM؟

Consider Reusable Architecture Assets in Phases A through D and Refine Their Use Later
⌄

يذكر الفصل أن Phases A إلى D تشير إلى مراحل النظر في reusable assets من Enterprise Architecture Continuum. يمكن ظهور Pattern مبكرًا لتشكيل Solution Concept ثم تتخصص عبر Business/Data/Application/Technology Architectures.

ADM Areaدور Pattern المحتمل
Phase Aصياغة high-level Solution Concept وبدائل معمارية.
Phase BBusiness patterns، operating model، capability collaboration.
Phase CData sharing، integration، application interaction.
Phase DPlatform، deployment، resilience، network patterns.
Phases E–Gاختيار SBBs، realization، governance، compliance مع intent.

25. Workflow لاختيار Pattern وتطبيقها

Search, Qualify, Tailor, Validate, Decide, and Record
⌄
1. Frame ProblemRequirements وConcerns وscope.
2. Describe ContextBaseline وconstraints.
3. Identify ForcesQuality trade-offs.
4. Search RepositoryPatterns وreference assets.
5. Compare CandidatesContext fit، evidence، risks.
6. Tailor & ModelStructure، behavior، variants.
7. Validate & RecordViews، decisions، resulting context.

أسئلة Qualification

  • هل Problem نفسها أم مجرد تشابه لغوي؟
  • هل Context وForces متوافقة؟
  • هل Known Uses موثوقة ومقاربة لحجمنا؟
  • هل Trade-offs مقبولة وفق Principles وRequirements؟
  • هل توجد Alternative Pattern أفضل؟

26. أخطاء شائعة وAnti-Pattern Thinking

Avoid Pattern Cargo Cults, Product Bias, and Context-Free Reuse
⌄
Pattern by Name Only

استخدام الاسم دون تعريف Context وForces وResult.

Product Disguised as Pattern

ربط Pattern بمورد واحد قبل Architecture Decision.

Ignoring Resulting Context

الاحتفال بالمزايا وإخفاء complexity أوcost الجديدة.

Pattern Everywhere

اعتبار الحل الشائع مناسبًا لكل حجم ونضج وdomain.

Diagram-Only Pattern

Structure بلا behavior أوRationale أوforces.

No Evidence

غياب Examples وKnown Uses يجعلها hypothesis أكثر من proven pattern.

28. مثال تطبيقي: Pattern لمنصة وطنية للمخزون الطبي

A Fully Structured Pattern from Recurring Problem to Resulting Context
⌄

Name

Federated Inventory Visibility.

Problem

الحاجة إلى رؤية وطنية شبه لحظية للمخزون دون استبدال أنظمة المستشفيات كلها.

Context

جهات متعددة، نظم heterogeneous، اتصال متفاوت، ownership محلي، regulation مركزي.

Forces

Timeliness مقابل bandwidth؛ central governance مقابل local autonomy؛ security مقابل ease of integration.

Solution

Canonical inventory events، local adapters، message broker، master item mapping، centralized visibility service، reconciliation workflow.

Resulting Context

تحسن visibility وdecisions، لكن تظهر مسؤولية إدارة canonical model وevent quality وadapter lifecycle.

Rationale

الفصل بين local systems وnational view يقلل replacement risk ويتيح onboarding تدريجيًا.

Related Patterns

Master Data، Event-Driven Integration، Offline Synchronization، API Gateway، Zero Trust Access.

Known Uses / Evidence

Pilot في ثلاث مناطق، قياس latency وcompleteness وincident reduction قبل التوسع.

المثال تعليمي مخصص لشرح قالب Pattern؛ ليس Pattern رسميًا مسمى في TOGAF.

29. مراجعة الامتحان والأسئلة التفاعلية

Part 1 Focus, Common Traps, and 32 Practice Questions
⌄

أهم الفروق الامتحانية

Building Block vs. Pattern

Building Block عنصر؛ Pattern توضح استخدام وترتيب العناصر في Context.

Problem vs. Context

Problem ما الذي نريد حله؛ Context متى وتحت أي شروط.

Forces vs. Requirements

Forces tensions وqualities تؤثر في trade-off؛ Requirements احتياجات مقبولة يجب تحقيقها.

Solution vs. Rationale

Solution ما التركيب والسلوك؛ Rationale لماذا يعمل.

Context vs. Resulting Context

الأولى قبل التطبيق؛ الثانية بعده مع trade-offs.

Example vs. Known Use

Example توضيح؛ Known Use تطبيق قائم يقدم evidence وقد يعمل كexample.

Architecture vs. Design vs. Idiom

Structural schema ثم component refinement ثم language-specific implementation.

Pattern vs. Product

Pattern generalized knowledge؛ Product قد يكون SBB يحققها.

خريطة الحفظ: Name → Problem → Context → Forces → Solution → Resulting Context → Examples → Rationale → Related Patterns → Known Uses.
