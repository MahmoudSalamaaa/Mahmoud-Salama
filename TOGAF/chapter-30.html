Architecture Content — Introduction

Structure the evidence of architecture so it can be understood, governed, reused, and evolved.

Study Chapter 30

1. لماذا توجد وثيقة Architecture Content؟

Define, Structure, and Present the Work Products Created by Architects
⌄

أثناء تنفيذ ADM ينتج المعماري Process Flows وRequirements وPlans وCompliance Assessments ومخرجات أخرى كثيرة. من دون نموذج موحد تصبح الأسماء والبنية ومستويات التفصيل مختلفة من فريق لآخر.

Consistent Definition

المنتج المعماري نفسه يحمل معنى مشتركًا عبر المشروعات والفرق.

Consistent Structure

المحتوى يُنظم بطريقة تسمح بالمقارنة والربط والتحليل.

Consistent Presentation

Stakeholders يتلقون Views ومخرجات مناسبة يمكن فهمها ومراجعتها.

الفكرة الأساسية: ADM يشرح عملية العمل، بينما Architecture Content يشرح شكل المحتوى الناتج وكيف يُنظم.

2. Content Framework كنموذج هيكلي

A Structural Model for Major Architecture Work Products
⌄

Content Framework يقدم Structural Model للمخرجات المعمارية الرئيسية؛ أي إنه لا يكتفي بقائمة وثائق، بل يحدد أنواع المحتوى وعلاقاتها وكيف يمكن وضعها داخل صورة معمارية كلية.

Architecture WorkDiscovery، analysis، modeling، decisions، and governance evidence.
→
Content FrameworkCategorizes and structures Deliverables، Artifacts، and Building Blocks.
→
Coherent Architecture DescriptionConsistent، navigable، reusable، and reviewable content.

3. TOGAF كإطار مستقل أومع أطر أخرى

Stand-Alone Use and Mapping to External Content Frameworks
⌄

صُمم TOGAF Content Framework ليتيح استخدام TOGAF كإطار قائم بذاته داخل المؤسسة، لكنه لا يمنع الجمع مع Content Framework خارجي مثل Zachman أوأطر حكومية أوصناعية أخرى.

Stand-Alone

اعتماد TOGAF Content Framework وEnterprise Metamodel كأساس المؤسسة.

Mapped Frameworks

استخدام TOGAF كمرجع وStarting Point لربط مخرجاته بإطار خارجي.

Organization-Specific

تكييف التصنيفات والكيانات والArtifacts بما يلائم احتياجات المؤسسة.

الهدف ليس فرض قالب عالمي، بل منع الغموض والفجوات مع السماح بالتكييف المقصود.

4. الفئات الثلاث للمخرجات المعمارية

Deliverables, Artifacts, and Building Blocks
⌄

Deliverable

Work Product محددة تعاقديًا وتخضع لمراجعة واعتماد وتوقيع رسمي.

Artifact

Work Product تصف جانبًا من Architecture؛ غالبًا Catalog أوMatrix أوDiagram.

Building Block

مكون Capability قابل محتملًا لإعادة الاستخدام ويمكن دمجه مع Building Blocks أخرى.

امتحانيًا: الكلمات ليست مترادفة. Deliverable حزمة رسمية؛ Artifact تمثيل أوView؛ Building Block هو الشيء المعماري الذي تصفه Artifacts.

5. Deliverable — المنتج الرسمي

Contractually Specified, Reviewed, Approved, and Signed Off
⌄

Deliverable مرتبطة عادة بنطاق العمل والعقد وAcceptance Criteria. قد تحتوي على Artifacts كثيرة، وقد تُسلّم في صورة وثيقة أوحزمة إلكترونية أوSnapshot معتمد.

Specifyتعريفها في Statement of Architecture Work أوProject Contract.
Produceتجميع المحتوى وArtifacts الضرورية.
ReviewStakeholder and governance review.
Approve / Sign-OffFormal acceptance and accountability.
Archive / TransitionRepository، reference model، standard، or landscape snapshot.

6. Artifact — وصف جانب من Architecture

An Artifact May Be Part of a Deliverable or a Deliverable in Its Own Right
⌄

Artifact تصف Aspect محددًا من Architecture. قد تكون جزءًا من Deliverable أكبر، وقد تعتبر Deliverable مستقلة إذا نصت المواصفات التعاقدية على ذلك.

مثال: Application Interaction Matrix غالبًا Artifact داخل Architecture Definition Document؛ لكنها قد تصبح Deliverable مستقلة إذا طلب العقد اعتمادها منفردة.

Artifacts تشكل جزءًا أساسيًا من محتوى Architecture Repository، لأنها تحمل المعرفة التي يمكن الرجوع إليها وتحديثها وإعادة استخدامها.

11. Building Block — مكون Capability قابل لإعادة الاستخدام

A Component Combined with Other Building Blocks to Deliver Architectures and Solutions
⌄

Building Block تمثل عنصرًا يمكن دمجه مع عناصر أخرى لتكوين Architecture أوSolution. قد تكون Business Capability أوProcess أوData Resource أوApplication Component أوTechnology Service.

Composability

تجميع عدة Building Blocks لإنشاء Capability أوسع.

Progressive Detail

تبدأ باسم ووصف مختصر ثم تتطور إلىSpecification كاملة.

Potential Reuse

قد تُنشر كStandard أوReference Model داخل Repository.

12. Progressive Elaboration للBuilding Blocks

From a Name to a Fully Specified and Decomposed Component
⌄
NameInventory Visibility Capability.
OutlinePurpose and boundary.
Logical DefinitionServices، data، behaviors، constraints.
DecompositionSupporting processes، apps، data، technology.
SpecificationStandards، interfaces، measures، ownership.

مستوى التفاصيل يجب أن يطابق مرحلة ADM والقرار المطلوب؛ لا حاجة لتفصيل Physical Products أثناء الرؤية المبكرة.

13. Architecture Building Block — ABB

Logical, Required, and Usually Supplier-Independent
⌄

ABB تصف ما هو مطلوب على مستوى منطقي أوغير مرتبط بمورد. قد تحدد Service مطلوبًا أوData Resource أوCapability، وتشكل Requirements التي يجب أن تحققها SBBs.

Business ABB

Supplier Qualification Capability.

Application ABB

Inventory Query Service.

Technology ABB

Highly Available Integration Platform.

14. Solution Building Block — SBB

Physical or Supplier-Specific Components that Realize ABBs
⌄

SBB تمثل مكونًا فعليًا أوSpecific Solution يحقق جزءًا أوكل ABB. قد تكون Product أوConfigured Service أوCustom Component أوOperational Process.

Business SBB

تفصيل عملية Supplier Qualification المعتمدة وأدوارها.

Application SBB

Implemented API أوCOTS Module يحقق Inventory Query.

Technology SBB

منتج Integration محدد وتكوينه وDeployment Topology.

15. ABB مقابل SBB

What Is Required versus How It Is Realized
⌄

ABB — Logical Need

Supplier-independent، يصف required capability والخدمات والبيانات والقيود. يجيب: ماذا نحتاج؟

→

SBB — Realization

Physical أوsupplier-specific، يحدد المكونات التي ستنفذ الحاجة. يجيب: بماذا وكيف سنحققها؟

ليس صحيحًا أن ABB دائمًا Business وSBB دائمًا Technology؛ كلا النوعين يمكن أن يوجد في Business وApplication وTechnology.

Architecture Description هي Work Product تستخدم للتعبير عن Architecture. Content Framework ينظمها، وArtifacts تقدم Views أوقوائم وعلاقات تصف Building Blocks التي تكوّن Architecture.

19. Content Framework مقابل Enterprise Metamodel

Categorization Structure versus Formal Model of Enterprise Entities and Relationships
⌄

Content Framework

يحدد Categorization Framework لتنظيم Architecture Description ومجموع Models وWork Products.

⇄

Enterprise Metamodel

يحدد أنواع Entities التي ستظهر في Models والعلاقات بينها، مثل Capability وProcess وApplication وData Entity.

Content Framework ينظم فئات المحتوى؛ Metamodel يحدد الأشياء والعلاقات التي يمكن نمذجتها.

20. لماذا نحتاج Enterprise Metamodel؟

A Starter Set, Completeness Check, and Basis for Analysis
⌄

Starter Set

تعطي المعماري قائمة أولية بأنواع الأشياء التي يجب بحثها وتغطيتها.

Completeness Check

تختبر مدى قدرة Modeling Language أوTool على تمثيل Entities وAttributes وRelationships المطلوبة.

Queryable Knowledge

تمكّن البحث والتصفية والتحليل وTraceability داخل Repository.

21. Consistency وCompleteness وTraceability

The Three Quality Outcomes of a Well-Defined Metamodel
⌄

Consistency

نفس المفهوم يحمل الاسم والمعنى والعلاقات نفسها عبر الفرق.

Completeness

الأنواع والعلاقات المهمة لا تضيع بسبب أداة أونموذج ناقص.

Traceability

يمكن تتبع Goal إلىRequirement ثم Capability وProcess وApplication وTechnology وRoadmap.

هذه النتائج تجعل Architecture أصلًا قابلًا للتحليل، لا مجموعة رسومات منفصلة جميلة المنظر فقط.

22. TOGAF لا يفرض Notation واحدة

ArchiMate, BPMN, UML, ERD, Flowcharts, or Any Suitable Notation
⌄

TOGAF لا يقيد اختيار Artifacts ولاModeling Notation. المهم أن تستطيع الوسيلة التعبير عن المعنى والعلاقات المطلوبة وخدمة Stakeholder Concerns.

ArchiMate

Cross-domain Enterprise Architecture modeling.

BPMN

Business Process behavior and flow.

UML

Software and system structure/behavior.

ERD / Flowchart

Data relationships or simple process logic.

الأداة أوNotation لا تصبح الهدف؛ يجب أن تتوافق مع Metamodel وتنتج Evidence يمكن فهمه وحوكمته.

23. ما الذي يؤثر في اختيار Content Framework؟

Architecture Framework and Supporting Software Tool
⌄

تذكر الوثيقة عاملين مباشرين: Architecture Framework الذي تتبناه المؤسسة، وSoftware Tool المستخدم لدعم Architecture Capability. عمليًا تضاف احتياجات Stakeholders والحوكمة والتكامل مع مستودعات المؤسسة.

Framework Fit

المصطلحات والمخرجات المطلوبة والمنهج المستخدم.

Tool Fit

قدرة الأداة على تمثيل Entities وRelationships وViews وQueries.

Enterprise Fit

العمليات الحالية والحوكمة والمهارات ومستوى النضج.

26. Content Framework وADM يعملان معًا

ADM Describes What to Do; Content Framework Describes What the Architecture Looks Like
⌄

ADM — Process

ينقل المؤسسة من Baseline إلىTarget عبر Visioning وArchitecture Definition وTransformation Planning وGovernance. يحدد Inputs وSteps وOutputs.

⇄

Content Framework — Structure

يفصل بنية Inputs وOutputs، ويضع كل Deliverable داخل Holistic Architecture View، ويحدد كيف تبدو Architecture عند اكتمال العمل.

جملة الحفظ الرسمية بالمعنى:
ADM tells you what to do; the Content Framework tells you what the completed architecture should look like.

⌄

29. مراجعة الامتحان والأسئلة التفاعلية

Part 1 Exam Focus, Common Traps, and 32 Practice Questions
⌄
Deliverable vs Artifact

Deliverable رسمية ومحددة تعاقديًا؛ Artifact تصف جانبًا وقد تكون جزءًا منها.

Artifact vs Building Block

Artifact هي التمثيل؛ Building Block هو العنصر أوCapability الموصوفة.

Catalog vs Matrix

Catalog قائمة؛ Matrix علاقات بين أنواع من العناصر.

ABB vs SBB

ABB الحاجة المنطقية؛ SBB المكون الفعلي أوsupplier-specific.

Content Framework vs Metamodel

الأول يصنف المحتوى؛ الثاني يحدد Entities وعلاقاتها.

ADM vs Content Framework

ADM العملية؛ Content Framework شكل وتنظيم المخرجات.

خريطة الحفظ:
Deliverable contains Artifacts → Artifacts describe Building Blocks → Content Framework organizes Architecture Descriptions → Enterprise Metamodel defines Entities and Relationships → Repository stores and reuses approved content.
