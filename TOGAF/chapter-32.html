1. غرض الفصل وخريطته

Architectural Artifacts: Concepts, Views, Viewpoints, Models, and the Complete ADM Artifact Inventory
⌄

هذا الفصل لا يكتفي بتعريف Catalog وMatrix وDiagram؛ بل يشرح كيف تُبنى Architecture Description حول Stakeholders وConcerns، وكيف يُختار Viewpoint وتُنشأ View، ثم يقدم جميع Artifacts الموصى بها حسب ADM Phase.

System-of-Interestالموضوع الذي نريد فهمه أوتغييره.
Stakeholdersأصحاب المصلحة في النظام.

الفكرة المركزية: لا تنتج Artifact لأنها موجودة في قائمة TOGAF؛ تنتجها لأن Stakeholder لديه Concern يحتاج View مناسبة وبقدر كافٍ من التفاصيل.

2. Environment وSystem وArchitecture

The Context, the System-of-Interest, and its Fundamental Concepts
⌄

Environment

السياق الذي يحدد كل المؤثرات على النظام: Developmental، Technological، Business، Operational، Organizational، Political، Economic، Legal، Regulatory، Ecological، وSocial.

System

مجموعة عناصر متفاعلة ومنظمة لتحقيق غرض أوأكثر.

Architecture

المفاهيم أوالخصائص الأساسية للنظام في بيئته، مجسدة في Elements وRelationships ومبادئ Design and Evolution.

حدود System-of-Interest تحدد ما يقع داخل التحليل وما يعتبر Environment خارجيًا. تغيير الحدود يغيّر Stakeholders وConcerns وArtifacts المطلوبة.

3. Architecture Description وArchitecture Model

A Work Product Composed of Views and Models
⌄

Architecture Description

Work Product يستخدم للتعبير عن Architecture؛ وهو مجموعة Architecture Views وModels توثق Architecture معًا.

Architecture Model

تمثيل لموضوع محل اهتمام، يكون أصغر أوأبسط أوأكثر تجريدًا من الواقع.

Selected Content

View قد تضم أجزاء مختارة من Model واحدة أوعدة Models لإثبات معالجة Concerns محددة.

إذن Architecture Description ليست Diagram واحدة، وModel ليست الواقع نفسه. هي تمثيلات مترابطة تتحكم فيها قواعد Metamodel وViewpoints.

4. العلاقة الرسمية بين Stakeholder وConcern وViewpoint وView وModel

How the Core Concepts Fit Together
⌄
Stakeholderله Interest في System-of-Interest، وقد يملك عدة Concerns.
Concernيؤطر الحاجة إلىViewpoint ويقود Requirements مثل Security أوAvailability.
Architecture Viewpointيحدد Conventions وModel Kinds لبناء وتفسير View.
Architecture Viewتمثيل فعلي للنظام من Perspective مجموعة Concerns ويضم Models.
Model Kindيحدد Conventions لنوع Modeling مثل Process Model أوData Model.
Architecture Modelالمحتوى الفعلي الذي يطبق Model Kind.
Architecture Descriptionتعبر عن Architecture من خلال Views وModels.
Viewpoint Libraryتخزن Viewpoint Specifications في Reference Library لإعادة الاستخدام.

5. Architecture View مقابل Architecture Viewpoint

What You See versus Where You are Looking From
⌄

Architecture Viewpoint

  • Specification أوSchema عام.
  • يحدد Stakeholders وConcerns وModel Kinds وConventions.
  • Generic وقابل للتخزين وإعادة الاستخدام.
  • مثل قالب “Executive Capability Viewpoint”.
→

Architecture View

  • المحتوى الفعلي الذي تراه.
  • خاص بArchitecture معينة.
  • ينفذ Viewpoint ويستخدم Models محددة.
  • مثل “2027 National Inventory Capability View”.
قاعدة الحفظ: View هي ما تراه؛ Viewpoint هي موضع النظر والقواعد التي تحدد ما ستراه وكيف تفسره.

7. اختيار Views: Completeness وIntegrity وFitness-for-Purpose

The Architect Must Balance Coverage, Coherence, and Practicality
⌄
Completenessهل تغطي Views جميع Concerns ذات الصلة بما يكفي للغرض؟
Integrityهل Views مترابطة ومتسقة ويمكن تتبع العناصر بينها؟
Conflict Reconciliationهل جرى حل Concerns المتعارضة وتوضيح Trade-offs مثل Security مقابل Performance؟
Fitness-for-Purposeإنتاج القدر اللازم للقرار، لا Modeling بلا نهاية كتمرين أكاديمي.

الاكتمال لا يعني توثيق كل شيء. يعني أن Architecture مناسبة للقرار والنطاق وStakeholders، وأن الثغرات المتبقية معروفة ومقبولة.

8. Baseline وTarget Views كأساس Gap Analysis

Develop Pertinent Views for Both Environments
⌄
Baseline Viewsكيف تعمل المؤسسة الآن؟ ما العناصر والعلاقات والقيود القائمة؟
→
Gap AnalysisRetain، Add، Remove، Replace، وتحليل أسباب الفروق.
→
Target Viewsكيف يجب أن تعمل المؤسسة مستقبلًا لمعالجة Concerns وRequirements؟

تطوير Views يتقدم غالبًا من Business إلىTechnology، ومن Overview إلىDetail، مع العودة المستمرة إلىConcerns وRequirements. وتُنشأ Views ذات الصلة لكل من Baseline وTarget في Phases B وC وD.

9. عملية إنشاء Architecture View

Reuse a Viewpoint, Select It, and Generate the View
⌄
Identify Stakeholdersمن يحتاج قرارًا أوفهمًا أوموافقة؟
Capture Concernsما الأسئلة والمخاطر والمتطلبات؟
Consult Viewpoint Libraryهل يوجد Viewpoint مجرب؟
Select Viewpointاختر الأنسب للConcerns.
Populate Modelsاستخدم Model Kinds واللغة المحددة.
Generate & Validate Viewاعرضها وتحقق من معالجة Concerns.

ISO/IEC/IEEE 42010 لا يفرض Process محددة، لكن TOGAF يوضح هذه الطريقة العملية عندما تكون Viewpoint Library ناضجة.

10. فوائد Viewpoint Library

Less Work, Better Understanding, and More Confidence
⌄

Less Architect Effort

القواعد وModel Kinds وNotation والأسئلة الأساسية معرفة مسبقًا، فتُنشأ Views أسرع.

Better Stakeholder Comprehension

Stakeholders يتعاملون مع شكل مألوف ولغة ثابتة بدل تعلم Diagram جديدة كل مرة.

Greater Confidence

Viewpoint لها Track Record معروف، ويمكن تقييم جودة Views مقارنة بقواعد ثابتة.

Viewpoint Library توجد داخل Reference Library في Architecture Repository، وتتحسن مع الاستخدام والGovernance.

11. عندما لا توجد Viewpoint مناسبة

Create a New Explicit Viewpoint or Start with an Ad Hoc View
⌄

Systematic Approach

عرّف Viewpoint جديدة رسميًا: Stakeholders، Concerns، Model Kinds، Notation، Validation Rules، ثم أنشئ View منها واحفظها لإعادة الاستخدام.

أو

Pragmatic Approach

أنشئ Ad Hoc View للحاجة الحالية، ثم قيّم لاحقًا هل يستحق Viewpoint الضمنية تعميمها وتوثيقها داخل المكتبة.

كل View لها Viewpoint ولو ضمنية. توثيقها صراحة يساعد في تقييم ما إذا كانت تغطي Concern فعلًا.

12. Views وTools وLanguages

Why Standard Semantics and Interoperable Tools Matter
⌄
Specialized ToolsProcess، Data، Application، Technology، Risk، Portfolio tools.
→
Common Architecture LanguageSemantics موحدة تسمح بإعادة الاستخدام وتبادل Architecture Description.
→
Integrated UnderstandingViews قابلة للمشاركة والتحليل بدل جزر من الرسومات المنفصلة.

اختلاف الأدوات طبيعي، لكن غياب لغة مشتركة يجعل دمج Views صعبًا. لذلك تساعد Standard Viewpoints وStandard Languages في Tool Interoperability وإعادة استخدام العناصر الأساسية.

13. مثال Pilot وAir Traffic Controller

Different Concerns, Different Viewpoints, Shared Safety Language
⌄

Pilot Viewpoint

  • Concerns: Fuel، passengers، altitude، speed، runway vector.
  • Model: Air Flight.
  • Tool: cockpit indicators.
  • Language: pilot-specific operational terms.
Shared
Radio
Language

Controller Viewpoint

  • Concerns: airspace، other aircraft، separation، traffic flow.
  • Model: Air Space.
  • Tool: radar.
  • Language: controller-specific traffic terms.

لا تصف أي View النظام كله. التداخل في Location وVector والاتصال المشترك ضروري للسلامة، ويبين لماذا تحتاج Viewpoints المختلفة لغة مشتركة عند نقاط التعاون.

14. مثال Users وDevelopers في Enterprise Architecture

Different Abstractions Must Still Intersect
⌄

User View

  • Availability وResponse Time.
  • سهولة Access to Information.
  • Business Processes enabled.
  • لا يحتاج رؤية DBMS أوتفاصيل Deployment.
↔

Developer View

  • Software، hardware، network، tools.
  • Maintainability وProductivity.
  • Interfaces وData Stores.
  • لا يرى Live Business Context بالطريقة نفسها.

المساحة المشتركة قد تشمل Processes التي يمكّنها النظام وقنوات الإبلاغ عن المشكلات. Architecture المتكاملة تحتاج ربط Views دون إجبار كل Stakeholder على استهلاك كل التفاصيل.

15. خلاصة View Development

Select the Stakeholder, Understand the Concerns, Model the Concerns
⌄
1. Select Key Stakeholderحدد صاحب القرار أوالتأثير أوالتأثر.
2. Understand & Generalize Concernsوثق الأسئلة والمصالح وأنواع Requirements.
3. Model and Address Concernsاختر Viewpoint وArtifact تحقق الفهم والقرار.

Concern قد تكون نوع Requirement عام مثل Availability ثم تنتج Requirements محددة. ربط Concerns بأنواع Artifacts يساعد Architect في اختيار ما يعرضه لكل Stakeholder.

16. Building Blocks وCatalogs وMatrices وDiagrams

How Metamodel Content Becomes Stakeholder-Usable Artifacts
⌄
Enterprise MetamodelEntity types، metadata، relationships، rules.
→
Building BlocksInstances مثل Business Service “Purchase Order”.
→
ArtifactsCatalogs، Matrices، Diagrams تعرض المحتوى.
→
Stakeholder AnswersOwnership، impact، support، dependency، compliance.

Catalog

قائمة Building Blocks من نوع واحد أوأنواع مترابطة لأغراض Reference وGovernance.

  • Best for inventory.
  • يحمل Metadata من Metamodel.
  • مثال: Application Portfolio.

Matrix

Grid تعرض علاقات بين نوعين أوأكثر من Entities، خاصة العلاقات القائمة على قوائم.

  • Best for cross-mapping.
  • مثال: CRUD Application/Data.
  • تكشف gaps وduplication.

Diagram

Graphical rendering لتوصيل Architecture Content أوتعبئته أوفحص اكتماله.

  • Best for structure and flow.
  • يمكن إنشاء عدة نسخ لConcerns مختلفة.
  • ليست بالضرورة الصورة الكاملة.

17. Repository Queries وAd Hoc Artifacts

Search, Filter, Query, and Generate Views On Demand
⌄

لأن Building Blocks وCatalogs تحمل Metadata، تستطيع EA Tools البحث والتصفية والاستعلام عن Architecture Repository، ثم توليد Catalogs وMatrices وDiagrams عند الطلب.

Ownership Query

أظهر كل Business Services التي تملكها Organization Unit معينة.

Impact Query

ما Processes وApplications وData التي ستتأثر بتغيير Technology Component؟

Compliance Query

ما Physical Components التي تستخدم Standards على وشك Retired؟

Ad Hoc Queries يجب أن تظل مرنة، ولذلك لا يحصرها Enterprise Metamodel في قائمة ثابتة. Metamodel تحدد البيانات والعلاقات التي تجعل الاستعلام ممكنًا.

تحتاج Structure أوFlow أوCommunication يسهل فهمه بصريًا.

29. مثال تطبيقي: منصة وطنية للمخزون الطبي

A Coherent Multi-View Architecture Description Built from One Governed Repository
⌄

Executive Concerns

Vision، public value، shortage reduction، regulatory compliance. Artifacts: Stakeholder Catalog، Value Chain، Business Model، Solution Concept.

Business & Operations

Capabilities، facilities، procurement، replenishment، recall. Artifacts: Capability Catalog، Value Stream/Capability Matrix، Process Flow، Business Event.

Data Governance

Medicine Item، Batch، Facility، Stock Event، ownership، CRUD، migration. Artifacts: Data Catalog، Data/Function Matrix، Application/Data Matrix، Lifecycle and Security Diagrams.

Application Architecture

Registry، inventory mobile، integration، analytics، alerts. Artifacts: Portfolio، Interface Catalog، Interaction Matrix، Communication and Migration Diagrams.

Technology Architecture

Cloud landing zone، identity، integration platform، network zones، resilience. Artifacts: Standards، Portfolio، App/Tech Matrix، Platform and Network Diagrams.

Delivery & Value

Work Packages، affected agencies، benefits and requirements. Artifacts: Project Context، Benefits Diagram، Requirements Catalog.

30. مراجعة الامتحان والأسئلة التفاعلية

Part 1 Exam Focus, Common Traps, and 32 Practice Questions
⌄
View vs Viewpoint

View محتوى فعلي خاص؛ Viewpoint Specification عامة وقابلة لإعادة الاستخدام.

Model vs View

Model تمثيل لموضوع؛ View قد تختار أجزاء من Models متعددة.

Catalog vs Matrix

Catalog inventory؛ Matrix relationships.

Matrix vs Diagram

Matrix علاقات قائمة/جدولية؛ Diagram بنية أوFlow بصري.

Completeness vs Detail

Completeness هي معالجة Concerns المناسبة، لا أقصى تفصيل.

Artifact List vs Mandatory Production

TOGAF يوصي بArtifacts؛ الاختيار Tailored وفق الغرض والنطاق.

Metamodel vs Artifact

Metamodel تحدد المعلومات والعلاقات؛ Artifact تعرض subset منها.

Baseline vs Target Views

كلاهما مطلوبان عند الحاجة لGap Analysis.
