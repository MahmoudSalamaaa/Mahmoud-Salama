1. غرض Chapter 4 وخريطته

Architecture Deliverables: The Formal Work Products Consumed and Produced Across the ADM
⌄

Deliverable هي Work Product تعاقدية أورسمية تُراجع وتُعتمد ويوقع عليها Stakeholders. هذا الفصل يشرح ما الذي تعنيه كل Deliverable، وما غرضها، وما المحتوى المعتاد لها، وكيف تتدفق بين مراحل ADM.

Business TriggerNeed، strategy، regulation، or change.
Request for Architecture WorkHigh-level trigger from sponsor.
Statement of Architecture WorkScope، approach، plan، acceptance.
Definition & RequirementsQualitative intent + measurable criteria.
Roadmap & Migration PlanWork packages، projects، schedule.
Contract & GovernanceCompliance، checkpoints، accountability.
Repository & ChangeReuse، lessons، Change Requests، new cycle.
المبدأ: Deliverables ليست قوالب جامدة؛ هي Baseline نموذجية تُكيف وفق المؤسسة والمشروع وStakeholders وProject Management Framework.

2. Deliverable مقابل Artifact مقابل Building Block

Formal Container, Descriptive Work Product, and Reusable Capability Component
⌄

Deliverable

Formal أوContractual Work Product. قد تحتوي عدة Artifacts، وتخضع Review وApproval وSign-off.

Artifact

Work Product تصف جانبًا من Architecture: Catalog أوMatrix أوDiagram.

Building Block

Component قابلة لإعادة الاستخدام؛ قد تكون ABB منطقية أوSBB تنفيذية.

مثال: Architecture Definition Document هي Deliverable، وتحتوي Business Footprint Diagram وApplication/Data Matrix كArtifacts، وهذه Artifacts تصف Capabilities وApplications وData Entities كBuilding Blocks.

3. لماذا يجب Tailoring وعدم نسخ القوالب حرفيًا؟

The Official Descriptions Are a Baseline, Not a Mandatory Document Set
⌄
External Referencesأشر إلىStrategic Plan بدل نسخه داخل Request for Architecture Work.
Enterprise Frameworksادمج مع PMBOK أوPRINCE2 أوCMMI أوAgile Delivery.
Stakeholder Needاختر Deliverables وArtifacts التي تدعم القرار والGovernance.
Downstream Impactلا تتجاهل عنصرًا دون تقييم؛ النقص قد يسبب مشكلة لاحقًا.

يمكن دمج Deliverables، تقسيمها، أوتمثيلها داخل Repository/Tool بدل ملفات منفصلة، طالما بقيت المعلومات المطلوبة واضحة وقابلة للتتبع والاعتماد.

5. Architecture Building Blocks — ABBs

Logical, Supplier-Independent Building Blocks from the Repository
⌄

Architecture Building Blocks (ABBs)

Architecture documentation and models from the enterprise Architecture Repository. ABBs تصف ما يلزم من Services، Data Resources، Capabilities، وLogical Components قبل اختيار حل محدد.

Output: FOutput: HInput: A–E
  • Logical أوsupplier-independent description.
  • تُستخدم في Baseline وTarget Architectures.
  • قد تُفكك إلىABBs أصغر.
  • تحدد Requirements يجب أن تحققها SBBs.
  • تُخزن وتُعاد استخدامها عبر Architecture Repository.

6. Architecture Contract

Joint Agreement on Deliverables, Quality, Conformance, and Fitness-for-Purpose
⌄
Development PartnersArchitecture team، implementation teams، suppliers.
↔
Architecture ContractScope، principles، requirements، conformance، roles، measures، workplan، time windows.
↔
Sponsors & Governance BodyAuthority، accountability، review، audit، acceptance.

الغرض هو ضمان Continuous Monitoring، الالتزام بالمبادئ والمعايير، تحديد المخاطر، توضيح المسؤوليات وسلطة جهة الحوكمة.

Design & Development Contract

يركز علىScope، Architecture Principles، Conformance، delivery phases، joint workplan، metrics.

Business Users’ Contract

يركز علىStrategic Requirements، adopters، time window، business metrics، Service Architecture وSLA.

Exam Key

Architecture Contract ليست Procurement Contract فقط؛ هي أداة Architecture Governance.

7. Architecture Definition Document

The Qualitative Container for Baseline, Transition, and Target Architectures
⌄

هي الحاوية الأساسية للArtifacts المعمارية. تشمل Business وData وApplication وTechnology، وتغطي Baseline وTransition وTarget.

Architecture Definition Document

  • Qualitative view.
  • تشرح intent وrationale.
  • Models لكل Domain وState.
  • Gap وImpact Analysis.
  • Mappings to Landscape، standards، reference models، reuse.
↔

Architecture Requirements Specification

  • Quantitative/measurable view.
  • تحدد ما يجب علىImplementation Project تحقيقه.
  • Success measures وstandards وcontracts.
  • Interoperability وITSM requirements.
  • Constraints وassumptions.
Definition Document تقول: “ما Architecture المقصودة ولماذا؟” Requirements Specification تقول: “ما المعايير القابلة للقياس التي تثبت أن التنفيذ متوافق؟”

8. Architecture Principles

Enduring Rules that Guide Decisions from Mission to Results
⌄

Architecture Principles

قواعد وإرشادات عامة ودائمة نسبيًا تدعم كيفية تحقيق Mission. تشمل Business وData وApplication وTechnology Principles.

Output: PreliminaryOutput: A–DInput: PreliminaryInput: A–H
  • Name، Statement، Rationale، Implications.
  • توجه Requirements وArchitecture Decisions.
  • تستخدم فيTrade-offs وCompliance Reviews.
  • تتغير نادرًا وتحتاج Governance.
  • قد توجد على Enterprise وSegment وDomain levels.

9. Architecture Repository

The Managed Holding Area for Projects, Reusable Assets, Standards, and Landscape Snapshots
⌄

Repository تسمح للمشروعات بإدارة Deliverables، العثور علىReusable Assets، ونشر المخرجات إلىStakeholders. هي ليست Folder فقط؛ بل Managed Knowledge Base لها تصنيف وOwnership وLifecycle.

Architecture MetamodelEntities، relationships، rules.
Architecture LandscapeBaseline، Transition، Target states.
Reference Library & StandardsPatterns، reference models، approved standards.
Governance LogDecisions، dispensations، compliance، lessons.

12. Architecture Vision

An Early, Formally Agreed Summary of the Enterprise Change and Outcome
⌄

Architecture Vision

تلخص التغيير المتوقع من Target Architecture وتمنح Stakeholders Outcome متفقًا عليه مبكرًا، حتى يركز الفريق بعدها علىDetail وFeasibility.

Output: AOutput: EInput: B–HInput: Requirements Management
  • Problem description and stakeholders/concerns.
  • Issues/scenarios to address.
  • Objective of Statement of Architecture Work.
  • Summary views such as Value Chain and Solution Concept Diagram.
  • Mapped requirements.
  • Reference to Draft Architecture Definition Document.

13. Business Principles, Business Goals, and Business Drivers

The Business Context that Explains Why Architecture Work Exists
⌄

هذه المجموعة تقدم Context لArchitecture Work: الاحتياجات، طريقة العمل، Direction، والظروف الخارجية التي قد تؤثر على التصميم رغم أنها ليست Architecture Content بحد ذاتها.

Business Driver

قوة أوضغط يخلق الحاجة إلىالتغيير: regulation، competition، cost، growth.

Business Goal

نتيجة طويلة أوعالية المستوى تريد المؤسسة تحقيقها.

Business Principle

قاعدة مستقرة توجه قرارات الأعمال وطريقة العمل.

14. Capability Assessment

Assess Enterprise, IT, Architecture, and Transformation Readiness Before Detailed Definition
⌄

IT CapabilityChange maturity، operations maturity، capacity، organizational impact.
Architecture CapabilityGovernance، skills، landscape، standards، reference models، reuse potential.

الغرض ليس تقييم Technology فقط؛ بل اختيار أسلوب ومستوى Formality وDetail مناسب لقدرة المؤسسة علىالتحول والتنفيذ والحوكمة.

23. Solution Building Blocks — SBBs

Implementation-Specific Building Blocks that Realize ABBs
⌄

ABB

  • What capability/service is required?
  • Logical and supplier-independent.
  • Defines requirements for realization.
  • Examples: Identity Service، Master Data Capability.
→

SBB

  • How will it be implemented?
  • Physical or supplier-specific.
  • Product، service، configured component، organization unit.
  • Examples: specific IAM platform، cloud database، outsourced service.

SBBs تظهر كOutput من Phase G وتعود إلىRepository لإعادة الاستخدام في دورات ADM لاحقة.

25. Tailored Architecture Framework

Tailor Once for the Enterprise, Then Tailor Again for the Specific Project
⌄

Enterprise-Level Tailoring

  • Integrate management frameworks.
  • Customize terminology and presentation.
  • Select and deploy tools.
  • Align with culture، commercial model، capability maturity.
→

Project-Level Tailoring

  • Select suitable ADM activities.
  • Choose Deliverables and Artifacts.
  • Set depth، formality، and checkpoints.
  • Address stakeholder and project needs.

المحتوى المعتاد: Tailored Method، Tailored Content، configured tools، interfaces معBusiness Planning، EA، Portfolio/Program/Project Management، System Development، وOperations.

26. أهم الأزواج التي يجب عدم الخلط بينها

Critical Exam Distinctions among Formal Architecture Work Products
⌄
Request vs Statement

Request يطلق العمل؛ Statement يحدد Scope وApproach وPlan وAcceptance.

Vision vs Definition

Vision ملخص مبكر متفق عليه؛ Definition وصف تفصيلي متعدد Domains وStates.

Definition vs Requirements Specification

Qualitative intent مقابل measurable compliance criteria.

Roadmap vs Migration Plan

Architecture path and work packages مقابل executable projects, resources, cost, schedule.

Governance Model vs Architecture Contract

Model يحدد processes/roles/checkpoints؛ Contract اتفاق رسمي علىdeliverables/conformance/quality.

Change Request vs Requirements Impact Assessment

Change Request يقترح تغييرًا أودورة جديدة؛ Impact Assessment تحلل أثر معلومات جديدة علىRequirements.

ABB vs SBB

Logical requirement مقابل implementation-specific realization.

Repository vs Deliverable

Repository managed store؛ Deliverable formal work product قد تنتقل إليه بعد الاعتماد.
