1. خريطة الفصل والغرض منه

Building Blocks: Reusable Capability Components, ABB/SBB Specifications, and Their Evolution through the ADM
⌄

Building Block ليست مجرد مربع في Diagram. هي حزمة Functionality أوCapability لها Boundary وInterfaces وعلاقات، ويمكن دمجها مع Building Blocks أخرى لتقديم Architecture أوSolution.

Architecture NeedBusiness goals، requirements، constraints، standards، stakeholder concerns.
→
Building Block SystemABBs تصف المطلوب منطقيًا؛ SBBs تحقق المطلوب بمنتجات ومكونات وعمليات فعلية.
بنية الفصل الرسمي: Introduction to Building Blocks ثم Building Blocks and the ADM.

2. التعريف العام لـBuilding Block

A Package of Functionality Defined to Meet Business Needs across an Organization
⌄

Building Block هي Package of Functionality تُعرّف لتلبية Business Needs على مستوى المؤسسة. قد تمثل Actor أوBusiness Service أوApplication أوData Entity أوTechnology Service، وفق Metamodel المؤسسة.

Business Meaningتبدأ من حاجة أعمال، لا من منتج تقني عشوائي.
Recognizable Thingلها هوية وحدود مفهومة لدى Domain Experts.
Composableتُجمع مع Blocks أخرى لتقديم Capability أوسع.
Potentially Reusableيمكن إعادة استخدامها في Architectures وحلول متعددة.

3. الخصائص العامة الرسمية

Type, Boundary, Interoperation, Assembly, Reuse, Replaceability, and Specification
⌄
Metamodel TypeActor، Service، Application، Data Entity، Component...
Defined Boundaryما داخل مسؤوليتها وما يقع خارجها.
Interdependentقد تعتمد على Blocks أخرى وتتفاعل معها.
Implementation-Awareتتطور لاستغلال Technology وStandards.
Assemblyيمكن تجميعها من Blocks أصغر.
Subassemblyقد تكون جزءًا من Block أكبر.
Reusable & Replaceableيفضل أن تستبدل دون انهيار Architecture.
Well-SpecifiedFunctionality وInterfaces وConstraints واضحة.

4. النوع وعلاقته بـEnterprise Metamodel

A Building Block Normally Has a Type Corresponding to the Metamodel
⌄
Metamodelيعرف Entity Types والعلاقات.
Entity TypeBusiness Service أوApplication Component مثلًا.
Building Block InstanceSupplier Qualification Service.
AttributesOwner، lifecycle، criticality، standards.
RelationshipsServes، uses، realizes، depends on.
Views & DecisionsCatalogs، matrices، diagrams، governance.

Metamodel تمنع أن يكون Building Block مجرد اسم حر بلا معنى أوعلاقات يمكن تحليلها.

5. Boundary — الحد المعماري

A Clear Boundary Makes the Block Recognizable, Governable, and Replaceable
⌄

Boundary تحدد Responsibility وInputs وOutputs وOwnership. Domain Experts يجب أن يتعرفوا على Building Block كـ“شيء” متماسك، لا كتجميع عشوائي من وظائف غير مرتبطة.

Weak Boundary

  • Responsibilities متداخلة.
  • Interfaces غير واضحة.
  • Ownership موزع بلا Accountability.
  • الاستبدال يؤثر في كل النظام.
→

Strong Architectural Boundary

  • Purpose واضح.
  • Published interfaces.
  • Dependencies معروفة.
  • Implementation قابلة للتغيير.

A Block Can Be Assembled from Others and Can Itself Be Part of a Larger Block

Decomposition تساعد في توزيع المسؤولية، لكن الإفراط فيها يرفع Complexity وInterface Count. لذلك يحدد Scope والDecision المطلوب المستوى المناسب.

7. Loose Coupling بينSpecification وImplementation

The Boundary and Specification Should Be Loosely Coupled to How the Block Is Realized
⌄
Stable SpecificationPurpose، behavior، service levels، interfaces، security، manageability.
⇢
Multiple Possible RealizationsCustom build، COTS، SaaS، outsourced process، or another compliant implementation.

الهدف أن يمكن تحقيق Building Block بطرق مختلفة دون تغيير Boundary أوContract الخاص بها. هذا هو الأساس العملي للReplaceability وتقليل Vendor Lock-In.

8. Reusability وReplaceability

Good Blocks Improve Legacy Integration, Interoperability, and Future Flexibility
⌄
Reuseنفس Specification أوBlock تدعم عدة Architectures.
Replaceيمكن تغيير realization مع الحفاظ علىContracts.
Commonalityاكتشاف القدرات المشتركة يقلل التكرار.
Legacy Integrationتغليف Legacy كBlock قد يسهل دمجه بدل تفكيكه فورًا.
إعادة الاستخدام ليست هدفًا مطلقًا؛ Block يجب أن تلائم Context وRequirements، وإلا يصبح “reuse” إعادة استخدام للمشكلة نفسها.

9. Interoperability وStable Interfaces

Systems Are Collections of Interacting Blocks, So Interfaces Must Be Published and Reasonably Stable
⌄
Service InterfaceOperations، messages، behavior.
Data InterfaceSemantics، format، quality، ownership.
Security InterfaceIdentity، authorization، audit.
Operational InterfaceMonitoring، support، incidents، SLA.
Change InterfaceVersioning، compatibility، deprecation.

Interface stability لا تعني عدم التغيير؛ تعني أن التغيير مُدار، versioned، ومفهوم للBlocks المعتمدة عليها.

10. Progressive Definition — التطور التدريجي

From a Name or Outline to Decomposition and Full Specification
⌄
NameIdentity only.
OutlinePurpose and boundary.
Logical DefinitionFunctions، services، data، constraints.
RelationshipsInterfaces and dependencies.
DecompositionSupporting blocks.
Full SpecificationStandards، qualities، performance، topology.

Definition تتطور مع ADM؛ لا ينبغي انتظار Full Specification قبل التحقق من Vision وStakeholder Agreement.

11. Just Enough Detail

The Required Detail Depends on Architecture Objectives; Less Detail Can Sometimes Deliver More Value
⌄

Executive Capability View

صورة واضحة ومختصرة قد تكون أكثر قيمة من 100 صفحة؛ الهدف هو Decision وAlignment.

Architecture Design View

تحتاج Functionality وInterfaces وRelationships وStandards وConstraints.

Implementation View

تحتاج Products، configuration، topology، performance، operation، security.

المعيار ليس “أكثر تفاصيل = Architecture أفضل”، بل “هل التفاصيل كافية للقرار والحوكمة والتنفيذ؟”.

12. Architecture Building Blocks — ABBs

Architecture-Continuum Building Blocks Defined or Selected through the ADM
⌄

ABBs ترتبط بـArchitecture Continuum، وتُعرّف أوتُختار كنتيجة لتطبيق ADM. وهي تلتقط Architecture Requirements وتوجه تطوير SBBs.

ABB — What Is Required?

  • Logical أوsupplier-independent.
  • Captures Business/Data/Application/Technology requirements.
  • Specifies required services، resources، capabilities.
  • Shapes SBB specifications.
  • May be reused as reference architecture content.
→

Examples

  • Secure Identity Service.
  • Trusted Master Data Capability.
  • Highly Available Integration Service.
  • Supplier Qualification Process.
  • Enterprise Audit Capability.

13. خصائص ABB الرسمية

Capture Architecture Requirements and Direct the Development of SBBs
⌄
Capture RequirementsBusiness، Data، Application، Technology.
Guide SBBsتضع expected capability وqualities.
Logical Orientationتركز على required architecture لا vendor.
Architecture Continuumتتحرك من Foundation إلىOrganization-Specific.
امتحانيًا: ABB لا تساوي “concept فقط”. قد تكون Specification دقيقة، لكنها تظل تصف المطلوب معماريًا لا المنتج المحدد.

14. الحد الأدنى لمحتوى ABB Specification

Fundamental Functionality, Interfaces, Interoperability, Dependencies, and Organizational Mapping
⌄
Minimum ABB Specification ElementMeaningExample
Fundamental Functionality & AttributesSemantic, unambiguous, including security capability and manageability.Authenticated stock query with full auditability.
Interfaces — Chosen Set Suppliedالخدمات أوالتفاعلات التي تقدمها ABB.Query، reserve، release، notify.
Interoperability & Relationshipsكيفية تفاعلها مع Blocks الأخرى.Identity، MDM، notification، analytics.
Dependent Building BlocksFunctionality مطلوبة وأسماء user interfaces.Depends on Item Master and Facility Registry.
Business / Organization / Policy Mappingربط ABB بالجهات والسياسات التي تحكمها.Owned by Supply Directorate; retention policy applies.

15. Solution Building Blocks — SBBs

Solutions-Continuum Components that May Be Procured or Developed
⌄

SBBs ترتبط بـSolutions Continuum وتمثل مكونات التنفيذ الفعلية أوالمحددة للمورد. يمكن شراؤها أوتطويرها، وقد تحقق جزءًا من ABB أوABB كاملة أوعدة ABBs.

Required ABB

Highly Available Integration Service with encryption, monitoring, and 99.95% availability.

→

Candidate SBBs

  • Specific managed integration platform.
  • Configured API gateway and message broker.
  • Custom integration runtime.
  • Outsourced managed integration service.

16. خصائص SBB الرسمية

Define Products and Components, Define Implementation, Fulfil Business Requirements, and Be Vendor-Aware
⌄
Products & Componentsتحدد ما الذي سينفذ Functionality.
Implementationتوضح realization الفعلية.
Business Fitيجب أن تحقق Business Requirements.
Product/Vendor-Awareقد تتضمن vendor، version، service tier، configuration.

كون SBB vendor-aware لا يعني أنها Technology فقط؛ قد تكون Business Process مُشترى كخدمة أوApplication أوTechnology Component.

17. الحد الأدنى لمحتوى SBB Specification

Specific Functionality, Implemented Interfaces, Topology, Shared Qualities, Performance, Constraints, and ABB Mapping
⌄
Minimum SBB Specification ElementMeaningExample
Specific Functionality & Attributesالوظائف الفعلية ومواصفات المنتج أوالمكون.API throttling، event delivery، audit logs.
Implemented Interfacesمجموعة Interfaces المنفذة بالفعل.REST v2، AMQP، admin console.
Required SBBs & Interfaces Usedالمكونات التي تعتمد عليها والواجهات المستخدمة.IAM OAuth endpoint، database driver.
IT Topology & Operational PoliciesMapping إلىDeployment والOperations.Two regions، active-active، on-call policy.
Shared Environmental AttributesSecurity، manageability، localizability، scalability.Central logging، Arabic UI، horizontal scaling.
Performance & ConfigurabilityThroughput، latency، tunable settings.5,000 messages/sec; configurable retention.
Design Drivers & ConstraintsPhysical architecture والقيود.Data residency، existing network zones.
SBB–ABB Relationshipsما الذي تحققه من ABBs وبأي Coverage.Realizes Integration ABB and part of Audit ABB.

18. ABB مقابل SBB

Logical Required Capability versus Physical or Supplier-Specific Realization
⌄

Architecture Building Block

  • What must exist?
  • Architecture Continuum.
  • Captures requirements.
  • Supplier-independent where practical.
  • Guides solution design.
realized by →

Solution Building Block

  • What will implement it?
  • Solutions Continuum.
  • Product/component/process specific.
  • Procured ordeveloped.
  • Mapped back to ABBs and requirements.
العلاقة ليست دائمًا واحدًا إلىواحد: ABB قد تتحقق بعدة SBBs، وSBB قد تحقق أجزاء من عدة ABBs.

19. Architecture Continuum وSolutions Continuum

Classify the Required Architecture and the Realizing Solutions as Related but Distinct Assets
⌄

Architecture Continuum

  • Foundation Architectures.
  • Common Systems Architectures.
  • Industry Architectures.
  • Organization-Specific Architectures.

ABBs تتحرك من generic إلىspecific.

Solutions Continuum

  • Foundation Solutions.
  • Common Systems Solutions.
  • Industry Solutions.
  • Organization-Specific Solutions.

SBBs تحقق Architecture assets على مستويات مختلفة.

20. Architecture Design كمجموعة Building Blocks مترابطة

An Architecture Is a Set of Building Blocks and a Specification of How They Connect to Meet Business Requirements
⌄
Business ServiceSupplier Qualification.
Data EntitySupplier Profile.
Application ServiceQualification Workflow.
Technology ServiceIdentity & Integration.
ControlsPolicy، security، audit، SLA.

Architecture ليست Inventory للBlocks فقط؛ القيمة في كيفية اتصالها لتلبية Overall Business Requirements.

21. Relevance وComplex Relationships

Include Only Blocks Relevant to the Business Problem, while Recognizing Many-to-Many Support Relationships
⌄

Architecture يجب أن تحتوي فقط Building Blocks ذات الصلة بالمشكلة. لكن العلاقات قد تكون معقدة: Block واحدة قد تدعم عدة Blocks، أوقد تدعم جزءًا فقط من Block أخرى.

One-to-Many

22. Conformance to Principles and Standards

Every Block Should Conform to Standards Relevant to Its Type and to Enterprise Principles
⌄
Type StandardsData modeling، API، security، platform standards.
Enterprise PrinciplesData is an asset، reuse before buy، interoperability.
Architecture StandardsApproved patterns، reference models، technology standards.
Governance EvidenceOwner، lifecycle، compliance status، dispensations.

Conformance تحول Building Blocks من تصميم محلي إلىArchitecture قابلة للتكامل والحوكمة على مستوى المؤسسة.

23. فئات التصميم الثلاث: Reuse أوDevelop أوPurchase

Classify Candidate Blocks as Reusable Legacy, New Development, or COTS Purchase
⌄

Reuse Existing

Legacy item أوapproved reusable block. يحتاج Fit Assessment وInterfaces وLifecycle Review.

Develop

New application، service، process، or component عندما لا توجد realization مناسبة.

Purchase

COTS/SaaS/managed service. يحتاج requirements fit، interoperability، embedded-process، vendor-risk analysis.

التصنيف لا يحسم القرار وحده؛ هو يوضح Realization Path الذي سيؤثر في Work Packages وProcurement وRisk.

24. Desired Level of Integration

Use the Desired Integration Level to Bind or Separate Functions into Blocks
⌄
Coarse-GrainedLegacy system كBlock كبيرة لتجنب تفكيكها مبكرًا.
Service-OrientedFunctions حول stable business services.
Fine-Grainedتفصيل أكبر لقرارات implementation أوreuse.
FederatedBlocks مستقلة مع standards وinterfaces مشتركة.

في المستويات العليا تُحفظ Blocks broad لعرض Services بوضوح؛ مع اقتراب التنفيذ تظهر Views أكثر تفصيلًا لقرارات products وcommonality وimpact.

25. التطور عبر ADM

Building Block Definition Is Gradual, Evolutionary, and Iterative — Mainly through Phases A, B, C, and D
⌄
Phase AHigh-level candidate building blocks.
Phase BBusiness ABBs and baseline/target gaps.
Phase CData and Application ABBs; candidate SBB implications.
Phase DTechnology ABBs، standards، platform realization options.
Phase EAssociate BB gaps with work packages.
Phase FSequence delivery and migration.
Phase GGovern realization and conformance.
RepositoryPublish reusable assets and update landscape.

التعريف Iterative لأن Functionality وConstraints وAvailable Products قد تغير اختيار وحدود ومحتوى Blocks.

26. Phase A — High-Level Candidate Building Blocks

Use a Coarse Model to Establish Vision, Scope, and Candidate Capability Structure
⌄

Candidate Model

تحديد Blocks الرئيسية اللازمة لإظهار Solution Concept وValue، دون الغرق في products.

Scope Boundary

ما الذي يقع داخل Architecture Work وما الذي يظل External Dependency.

Repository Reuse

البحث عن existing capabilities، reference architectures، standards، وlegacy blocks.

Phase A لا تختار Vendor تفصيليًا؛ تبني فهمًا كافيًا للVision والFeasibility والStakeholder Agreement.

27. Phases B/C/D — دورة التحديد والتوثيق الرسمية

Baseline, Target, Gap, Roadmap, Landscape Impact, Review, Finalization, and Architecture Definition
⌄

1–3: Model

  • Select reference models, viewpoints, and tools.
  • Model existing blocks, reusing Repository definitions.
  • Develop required blocks through catalogs, matrices, diagrams.

4–6: Analyze

  • Carry over، eliminate، or add blocks.
  • Determine develop/procure realization.
  • Resolve impacts across Architecture Landscape.

7–9: Govern & Publish

  • Formal Stakeholder Review.
  • Fully document blocks and decision rationale.
  • Select standards، map to Landscape، publish reusable assets.

العمل الأكبر هو تحديد ABBs اللازمة لتحقيق Business Goals، ثم refinement iterative للوصول إلىSBBs يمكن شراؤها أوتطويرها.

28. Gap Analysis، Work Packages، Governance، Requirements، وRepository

Connect Carried-Over, Eliminated, and New Blocks to Delivery and Long-Term Reuse
⌄

30. مراجعة الامتحان والأسئلة التفاعلية

Part 1 Exam Focus, Common Traps, and 32 Practice Questions
⌄
Building Block vs Artifact

Block هي capability component؛ Artifact هي تمثيل يصفها.

ABB vs SBB

ABB تصف المطلوب معماريًا؛ SBB تصف realization الفعلية.

Logical vs Vague

ABB قد تكون دقيقة جدًا، لكنها غير مرتبطة بمنتج بعينه.

Reuse vs Fit

لا تعِد الاستخدام إلا بعد التحقق منContext وRequirements.

Stable Interface vs Frozen Interface

Stable يعني managed/versioned، لا ممنوع التغيير.

More Detail vs More Value

مستوى التفاصيل يتبع decision وphase وstakeholders.

One ABB vs One SBB

العلاقة قد تكون many-to-many.

Inventory vs Architecture

Architecture تشمل Connections وConstraints، لا قائمة Blocks فقط.
