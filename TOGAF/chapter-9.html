1. موضع Phase C والغرض منها

Information Systems Architectures: Data and Application
⌄

تأتي Phase C بعد Business Architecture. وهي تحول متطلبات وقدرات وخدمات الأعمال إلى معماريتين مترابطتين: Data Architecture وApplication Architecture.

Data Architecture

تحدد البيانات المطلوبة، معناها، ملكيتها، مكوناتها المنطقية والمادية، تدفقها، إدارتها، حمايتها، وهجرتها.

Application Architecture

تحدد الخدمات والمكونات التطبيقية التي تدعم الأعمال والبيانات، وكيف تتفاعل وتتوزع وتتطور وتُشغّل.

الفكرة الكبرى: Phase C لا تصمم قواعد بيانات أوشاشات تفصيلية فقط؛ بل تبني Blueprint متكاملًا للمعلومات والتطبيقات يخدم Business Architecture ويقيد Phase D Technology Architecture.

2. Objectives — أهداف Phase C

Target Information Systems Architectures and Gap-Based Roadmap Candidates
⌄

Develop Target Information Systems Architectures

تطوير Target Data وApplication Architectures بطريقة تمكّن Business Architecture وArchitecture Vision وتستجيب لStatement of Architecture Work وStakeholder Concerns.

Identify Candidate Roadmap Components

استخراج مكونات أولية للRoadmap من الفجوات بين Baseline وTarget في البيانات والتطبيقات.

احفظ: Target Data + Target Application + Gap-Based Roadmap Components.

3. أيهما أولًا: Data أم Application؟

Data-Driven, Application-Driven, or Iterative Combination
⌄

يمكن تنفيذ Data وApplication Architecture بأي ترتيب، أوبتكرار قصير بينهما. الاختيار يعتمد على Context.

Data-Drivenنبدأ من Information Needs وData Entities وOwnership وLifecycle، ثم نحدد التطبيقات التي تنشئ البيانات وتستخدمها. مناسب عندما تكون Master Data، Analytics، أوData Governance هي المحرك.
↔
Application-Drivenنبدأ من Core Applications أوERP/CRM/Platforms والقدرات التي تقدمها، ثم نفصل Data Ownership وFlows. مناسب عندما يكون برنامج إحلال أوتكامل التطبيقات هو المحرك.

غالبًا لا يكون القرار ثنائيًا بالكامل. قد تبدأ بالData ثم تدخل Iteration قصيرة للتطبيقات، أوالعكس، حتى يتحقق اتساق مشترك.

TOGAF لا يفرض Data قبل Application أوالعكس.

6. Data Architecture Objectives and Scope

Enable Business Architecture through Trusted, Governed, and Interoperable Data
⌄

تهدف Data Architecture إلى تطوير Target تصف البيانات ومكوناتها وعلاقاتها وطريقة إدارتها، ثم استخراج Roadmap Candidates من الفجوات.

Conceptual Focus

Business Data Entities والمعنى المشترك والعلاقات الأساسية التي يفهمها أصحاب الأعمال.

Logical Focus

Logical Data Components المطلوبة عبر التطبيقات دون الارتباط بمنتج أوقاعدة بيانات محددة.

Physical Awareness

Physical Data Components الموجودة أوالمطلوبة، مثل Schemas وMessages وFiles وStores.

Management Focus

Ownership، Quality، Security، Metadata، Lifecycle، Migration، Distribution، وArchiving.

7. أنواع البيانات التي يجب أن تغطيها Architecture

Data at Rest, in Motion, in Use, and Open Data
⌄
Data at Restالبيانات داخل Databases، Warehouses، Files، Archives، وStores.
Data in Motionالبيانات أثناء Transactions، Events، Messages، Services، وAPIs.
Data in Useالبيانات عند حدود التطبيق والمستخدم مثل Forms، Screens، Reports، وExports.
Open Dataبيانات تقدمها المؤسسة للاستخدام العام طوعًا أوبموجب متطلبات قانونية.

إهمال أحد الأنواع ينتج Architecture ناقصة؛ فData Model قد يكون ممتازًا بينما API Semantics أوPublic Data Controls غير واضحة.

8. Data Metamodel: Entity, Logical Component, Physical Component

Move from Business Meaning to Logical Organization and Physical Implementation
⌄
Data Entityمفهوم أعمال مثل Product، Supplier، Patient، Order. يستخدم في Conceptual Models.
→
Logical Data Componentتنظيم منطقي لمجموعة بيانات يحدد المتطلبات دون تقنية تنفيذية.
→
Physical Data Componentتنفيذ فعلي أوRequirement للتنفيذ مثل Database Schema أوXML/JSON Message.
Data Entity ليست Table بالضرورة، وLogical Data Component ليست Database Product.

9. Select Data Reference Models, Viewpoints, and Tools

Model the Concerns of Regulators, Owners, Users, Generators, Subjects, and Auditors
⌄

تراجع Data Principles ثم تختار Reference Models وPatterns وViewpoints بناءً على Business Drivers وStakeholders وBusiness Architecture.

Viewpoint Dimensions

  • Regulators، users، generators، subjects، auditors.
  • Real-time، event-driven، reporting period.
  • Locations، processes، security zones.

Tools

  • Documents وSpreadsheets.
  • Data Catalog وMetadata Tools.
  • ER/Class Modeling.
  • Data Lineage وGovernance Platforms.

Modeling Process

  • جمع النماذج من Business/Application.
  • Rationalize Requirements.
  • توحيد Inventory وSemantics.
  • ربط Data بالأعمال والتطبيقات.

11. Develop Baseline and Target Data Architecture

Describe Current Reality and the Future Data Environment at the Required Level of Detail
⌄

Baseline تجمع ما هو موجود: Enterprise Data، Local Spreadsheets، Schemas، Interfaces، Data Owners، Quality Issues، وLifecycle. Target تحدد المعنى المشترك والمكونات المطلوبة والتوزيع والأمن والإدارة والهجرة.

Baseline Questions

أين توجد البيانات؟ من ينشئها؟ من يملكها؟ ما التكرارات؟ ما جودة النماذج الحالية؟ ما Shadow Data؟

Target Questions

ما Source of Truth؟ ما Shared Entities؟ كيف يتم التبادل؟ ما Governance وQuality Rules؟ كيف تحفظ وتؤرشف؟

لا تعيد رسم كل Physical Schema قديم بلا قيمة. اختر مستوى التفاصيل الكافي لفهم Gaps وRoadmap.

12. Data Governance, Management, and Migration

Ownership, Quality, Security, Lifecycle, Metadata, and Controlled Transition
⌄

Data Governance

  • Accountability وDecision Rights.
  • Owners وStewards.
  • Policies وStandards وCompliance.

Data Management

  • Quality وMetadata.
  • Master/Reference Data.
  • Security وPrivacy.
  • Retention وArchiving.

Data Migration

  • Source-to-Target Mapping.
  • Cleansing وDeduplication.
  • Cutover وReconciliation.
  • Legacy Retention/Retirement.

Migration ليست نشاطًا تقنيًا مؤجلًا فقط؛ قيودها قد تغير Target Application وTechnology Architectures والRoadmap.

13. Data Gap Analysis and Roadmap Candidates

Turn Missing, Duplicated, Obsolete, and Inconsistent Data Capabilities into Change Components
⌄
NewMaster Data Service، Metadata Catalog، Data Quality Capability، New Entity/Component.
Modifiedتغيير Ownership، Schema، Interface، Classification، Retention، أوQuality Rule.
Retainedمكونات حالية مناسبة تُحمل إلى Target وتُدعم.
RemovedDuplicate Stores، Obsolete Files، Unused Interfaces، Shadow Databases.
Migration WorkCleansing، Mapping، Historical Load، Archive، Cutover.
Governance WorkOwnership، Stewardship، Standards، Quality KPIs، Compliance.

14. Finalize and Publish the Data Architecture

Standards, Building Blocks, Traceability, Repository Mapping, and Formal Documentation
⌄

في Finalize يتم اختيار Standards، توثيق Building Blocks، Cross-check مع Business Requirements، تسجيل Rationale، إكمال Requirements Traceability، وتحديد الأصول القابلة لإعادة الاستخدام في Repository.

Architecture Definition Document

  • Business Data Model.
  • Logical Data Model.
  • Data Management Process Models.
  • Data Entity/Business Function Matrix.
  • Data Interoperability Requirements.

Requirements & Roadmap

  • Gap Results.
  • Interoperability and Security.
  • Constraints on Technology Architecture.
  • Updated Business/Application Requirements.
  • Data Roadmap Components.

15. Application Architecture Objectives and Scope

Define the Application Services and Components that Enable Business and Data
⌄

تطور Target Application Architecture وتحدد Roadmap Candidates من Gaps. التركيز على What applications/services are needed، وليس تصميم Source Code أوUI تفصيلي.

Application Servicesالسلوك الآلي الذي تستهلكه الأعمال أوتطبيقات أخرى.
Logical Componentsوظائف تطبيقية مستقلة نسبيًا عن المنتج.
Physical ComponentsSystems، Products، Packages، Deployments موجودة أومستهدفة.
InteractionsInterfaces، Events، APIs، Data Exchanges، User/Location Dependencies.

16. Select Application Reference Models, Viewpoints, and Tools

Use the Repository, Principles, Stakeholder Concerns, and Appropriate Modeling Depth
⌄

تراجع Application Principles وتختار Models وPatterns من Repository. من الموارد الممكنة Industry Application Models وCommon Function Models وIII-RM عند الحاجة إلى Integrated Information Infrastructure.

Viewpoints

Business User، Product Owner، Integration، Operations، Security، Support، Location، Lifecycle.

Tools

Application Portfolio، EA Repository، UML/ArchiMate، API Catalog، CMDB، Integration Modeling.

Required Detail

Granularity تكفي لتحديد Gaps وCandidate Work Packages دون التحول إلى Detailed Solution Design.

17. Rationalize the Application Portfolio

Decompose, Remove Duplication, Combine Similar Functions, and Map Logical to Physical Applications
⌄
Inventoryجمع Baseline Application Portfolio.
Decomposeتفكيك التطبيقات المعقدة إلى Components مفهومة.
Rationalizeإزالة Duplicate Functionality وOverlaps.
Logical Modelتحديد Logical Applications/Services المطلوبة.
Physical Mappingربط Logical بالموجود أوالمنتج المستهدف.
ViewsIntegration، Migration، Development، Operations.
Application Rationalization لا يعني حذف كل Duplicate فورًا؛ بل كشف التكرار وتقييم القيمة والمخاطر والانتقال.

18. Application Catalogs, Matrices, and Diagrams

Create Traceability from Business Services and Data to Applications, Users, Locations, and Interfaces
⌄

Catalogs

Application Portfolio، Interface Catalog، Logical/Physical Application Components، Application Services.

Matrices

Application/Business Service، Application/Data Entity، Application/Organization، Role/Application، Interface/Application.

Diagrams

Application Communication، Application Use-Case، Software Distribution، Process/Application Realization، Enterprise Manageability.

ربط التطبيقات بBusiness Services هو مستوى مهم لاتخاذ القرار. ثم يمكن ربطها بالData عبر Business Information Models.

19. Develop Baseline and Target Application Architecture

Understand the Current Portfolio and Define the Future Application Landscape
⌄

Baseline

Current Systems، Interfaces، Users، Locations، Support Ownership، Lifecycle، Costs، Dependencies، Known Issues.

Target

Application Services، Logical Components، Target Portfolio، Integration Patterns، Data Responsibilities، Operating Model.

Existing Building Blocks قد تكون موثقة بما يكفي وتُحمل إلى Target. الجديدة تحتاج تعريفًا كافيًا. اختيار Product محدد يعتمد على Scope وAbstraction Level وقد يؤجل إلى Solution Architecture.

20. Application Interoperability and Integration

Define How Applications Exchange Services and Information without Losing Meaning or Control
⌄
Business Serviceالقيمة أوالسلوك المطلوب للأعمال.
→
Application Serviceالسلوك الآلي المتاح عبر Interface.
→
Integration ContractAPI/Event/Message، Semantics، Security، SLA، Versioning.
→
Technology ConstraintsMessaging، Platform، Network، Identity، Observability requirements for Phase D.

Interoperability Requirements لا تقتصر على الاتصال التقني؛ تشمل Data Meaning، Process Coordination، Security، Timing، Error Handling، وOwnership.

21. Application Gap Analysis and Roadmap Candidates

Identify New, Consolidated, Enhanced, Integrated, Migrated, and Retired Applications
⌄
New Services/Appsوظائف مطلوبة لا يوفرها Baseline.
Consolidateدمج تطبيقات متشابهة أووظائف مكررة.
Enhanceتوسيع تطبيق قائم لتغطية Gap.
IntegrateAPIs، Events، Shared Services، أوProcess Orchestration.
Migrate/Replaceنقل Data/Users/Processes إلى Target Application.
Retireإيقاف Application أوInterface أوComponent لم يعد مطلوبًا.

22. Cross-Domain Impacts, Stakeholder Review, and Iteration

Revisit Business or Data Architecture when Application and Data Decisions Reveal Significant Impacts
⌄

المراجعة الرسمية تقارن Architecture المقترحة بالدافع الأصلي وStatement of Architecture Work وتنفذ Impact Analysis.

Business ArchitectureProcesses، Services، Capabilities، Organization.
↔
Data ArchitectureEntities، Ownership، Flows، Governance.
↔
Application ArchitectureServices، Components، Interfaces، Portfolio.
→
Technology ArchitectureConstraints and required platform capabilities.

إذا كان التأثير كبيرًا، يجوز عمل Short Iteration للBusiness أوData أوApplication Architecture. التكرار هنا تصحيح مقصود، وليس فشلًا في المنهج.

A Combined Phase C Case Study
⌄
Business Needرؤية موحدة للمخزون والاستهلاك والطلبات.
Data InventoryProduct، GTIN، Entity، Store، Stock، Consumption، Supplier.
Data TargetMaster Data، ownership، quality rules، API schemas، history.
App BaselineERP، WMS، Portals، Mobile، Spreadsheets، BI.

مثال Matrix مختصر

Product Master ينشأ ويُحكم في MDM، تستهلكه Procurement وWMS وAnalytics. Stock Balance ينشأ في WMS ويُنشر Event/API، ولا يُعاد إنشاؤه يدويًا في كل نظام.

25. مراجعة الامتحان والأسئلة التفاعلية

Part 1 Exam Focus and 26 Practice Questions
⌄
Phase B vs. Phase C

B تصف الأعمال؛ C تصف البيانات والتطبيقات التي تمكّنها.

Data-Driven vs. Application-Driven

ترتيب Contextual وليس قاعدة ثابتة.

Entity vs. Logical vs. Physical Data

Meaning → Logical Organization → Implementation.

Application Service vs. Component

Service سلوك متاح؛ Component ينفذ السلوك.

Architecture vs. Detailed Design

Phase C تحدد Blueprint وRequirements، لا Code/Schema التفصيلي دائمًا.

Gap vs. Roadmap Candidate

Gap فرق؛ Roadmap Candidate تغيير مقترح لمعالجته.

Interoperability vs. Connectivity

Interoperability تشمل المعنى والأمن والتوقيت والاستخدام، لا الاتصال فقط.

Finalization vs. Publication

Finalize يغلق القرارات والArtifacts؛ Create/Update Document ينشرها رسميًا.

خريطة الحفظ:
Business Needs → Data & Application Models → Baseline/Target → Gaps → Roadmap Candidates → Landscape Impacts → Review → Finalize → Definition Document → Phase D Constraints.
